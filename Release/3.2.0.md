# RMVC 3.2.0

Optional command locks let related commands coordinate their work through facade-owned gates. Awaited child commands can now perform cleanup after cancellation while retaining their inherited abort state.

## Optional command locks

This is advanced, opt-in functionality. Most applications do not need it.

- Define a meaningful empty type implementing `IRCommandLock`.
- Register one instance through `RFacade.RegisterCommandLocks()`.
- Declare each command's requirements through `GetLocks()`, using `Lock<T>()` directly or an accessor on the application's `CommandBase`.
- RMVC acquires the requested gates before `Run()` and releases owned reservations after command exit handling, including failure paths.
- Awaited children and deeper descendants reuse ancestor reservations and can declare additional requirements. Each command independently declares everything it needs.
- Lock identities belong to one facade. Cross-facade sharing is not supported.

Locks coordinate participating commands. Models, proxies and views still own their local thread safety. Input validation, database transactions and stale-state checks remain application responsibilities.

Progress callback commands and their descendants must not declare locks. Duplicate declarations are reported through diagnostics and reserved once.

Detected circular waits are programming errors. RMVC delivers an unhandled `RCommandLockCycleException` after the affected root unwinds, even if an ancestor caught the descendant exception. This does not depend on logging.

## Child execution after cancellation

**Behaviour change:** ordinary awaited children can enter `Run()` when their inherited cancellation token is already cancelled. This also applies to facades that register no command locks.

The token and shared error history remain unchanged. `AbortRequested` and `ErrorOrAbort` remain true. Children must still acquire their declared gates; inherited cancellation does not cancel those waits.

This supports required cleanup in awaited children, including children executed from `finally`. Place cancellation checkpoints according to the operation's responsibilities. `ThrowIfAbortRequested()` and cancellation-aware IO still honour cancellation.

Roots retain cancelled-entry checks and cancellable gate waits. Cancellation and shutdown never forcibly release a gate underneath running work.

## Usage and compatibility

Await child commands sequentially. Do not discard their tasks or launch sibling children concurrently. Lock-enabled facades detect overlapping child execution and drain detected unfinished children before releasing reservations; this cannot prove every task was awaited or undo earlier overlap.

An awaited child failure can be recorded without being rethrown to its parent. Check `ErrorOrAbort` before dependent work or reporting success.

There is no FIFO, starvation-prevention or maximum-wait guarantee. Avoid holding gates across human decisions or unnecessarily lengthy operations.

The library continues to target **.NET Standard 2.0**.
